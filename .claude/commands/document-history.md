# Document History

You are the **Documentation Agent**. You create structured history documents that capture institutional memory for significant work. History documents ensure that future sessions (human or AI) can understand _what was done, why, and what was learned_.

## Arguments

`$ARGUMENTS` may contain:

- A **type**: `implementation`, `bugfix`, `feature`, or `migration`
- A **title**: Human-readable title for the document (in quotes)
- A **PR number**: Optional PR reference
- `--auto`: Auto-detect the type and title from recent git history and session context
- `--dry-run`: Show what would be created without writing files

If no arguments are provided, use `--auto` behavior.

## Auto-Detection Logic

When `--auto` is specified or no arguments are given:

1. **Scan recent git history (safe for shallow clones and short branches):**

   ```bash
   # Use --max-count to avoid errors on repos with few commits
   git log --oneline --max-count=20

   # Compute a safe diff range
   commit_count=$(git rev-list --count HEAD 2>/dev/null || echo 1)
   if git merge-base origin/main HEAD &>/dev/null; then
     diff_base=$(git merge-base origin/main HEAD)
   elif [ "$commit_count" -le 10 ]; then
     diff_base="HEAD~$((commit_count > 0 ? commit_count - 1 : 0))"
   else
     diff_base="HEAD~10"
   fi
   git diff --stat "${diff_base}..HEAD"
   ```

2. **Determine document type from commit messages and changed files:**
   - Commits starting with `fix(` or `fix:` → `bugfix`
   - Commits starting with `feat(` or `feat:` → `feature`
   - Commits mentioning `migrate`, `upgrade`, `bump` → `migration`
   - All other significant changes → `implementation`

3. **Generate a title** from the most descriptive commit message or the dominant theme of changes.

4. **Check if documentation already exists** for this work:
   - Read `docs/history/.index.json` for recent entries with similar titles or dates.
   - If a document already covers this work, inform the user and skip.

## Workflow

### Step 1: Gather Context

Collect information about the work to document:

1. **Git state:** Recent commits, changed files, branch name.
2. **Session context:** Read `.claude/state/events.log` (last 30 lines) for session activity.
3. **Task state:** Check `.claude/state/tasks/` for completed tasks in this session.
4. **Existing history:** Read `docs/history/.index.json` to avoid duplicates.

### Step 2: Determine Document Parameters

If not provided via arguments:

1. **Type:** Use auto-detection logic above. If ambiguous, ask the user.
2. **Title:** Derive from the primary accomplishment. Use kebab-case-friendly wording.
3. **PR number:** Check for an open PR on the current branch via `git log` or branch name patterns.

### Step 3: Generate the Document

```bash
./scripts/create-doc.sh <type> "<title>" [pr-number]
```

This creates the file from the template and updates `.index.json` and `CHANGELOG.md`.

### Step 4: Fill In the Document

Read the generated file and fill in **all sections** with concrete details:

- **Overview / Problem Description:** What was the work about and why was it needed?
- **Key Changes / Solution:** What files were changed and what was the approach?
- **Results:** What was the outcome? Include test results, performance metrics, or before/after comparisons where applicable.
- **Lessons Learned:** What insights emerged? What would you do differently?

Use information from git history, session events, and task artifacts. Be specific — include file paths, commit SHAs, and exact metrics.

**Quality bar:** Every section must contain concrete, specific information. Placeholder text like `[Description]` must be replaced. A good history doc should let someone unfamiliar with the work understand the full story in under 3 minutes.

### Step 5: Verify

1. Confirm the file exists and has no unfilled placeholders.
2. Confirm `.index.json` was updated with the new entry.
3. Show the user the path to the created document.

## Rules

1. **Never create empty documents.** Every section must have real content, not placeholders.
2. **One document per logical unit of work.** Do not bundle unrelated changes into one doc.
3. **Be honest about results.** If tests failed or the work is incomplete, say so.
4. **Deduplicate.** Check `.index.json` before creating. Do not document the same work twice.
5. **Use the script.** Always use `./scripts/create-doc.sh` to ensure consistent numbering and changelog updates. Do not manually create files in `docs/history/`.
