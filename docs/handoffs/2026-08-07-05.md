## What Was Done

Phases 1–2 made 38 agents registrable and derived write guardrails from `accepts`. The
rest of the `dispatch:` block was parsed and ignored. Phase 3 wires it up.

**`can-dispatch`.** Resolves per agent, defaulting by category. 13 coordinator agents
(team-creation, strategic-operations, project-management) keep the `Agent` tool; the other
25 receive `disallowedTools: Agent`. Worth stating plainly because the phasing table calls
Phase 3 "medium risk — enables fan-out and its token cost": it does the opposite. Before
this change all 38 agents inherited `Agent`. Phase 3 takes it away from 25 of them.

**`tools-mode: allowlist`.** Emits `tools:` from `preferred-tools`. The spec's emission
table would have produced `tools:` _and_ `disallowedTools:` for a read-only agent in this
mode — the same restriction stated twice, in two languages, with no documented precedence
between them. As shipped, `tools:` is the single authority: read-only denials are
subtracted from the list and `disallowedTools` is omitted. An allowlist resolving to
nothing falls back to `inherit` with a warning, because an empty `tools:` launches a
subagent with no tools at all and fails at its first tool call rather than at sync time.

**Overrides.** `isolation` (`auto | worktree | none`), `background`, `color`, and `model`
all override their derived values. An unrecognised `isolation` value falls through to
derivation rather than silently disabling it — the validator reports the typo.

**Model routing.** Live per the spec table: `haiku` on the four watcher agents
(coverage-tracker, dependency-watcher, roadmap-tracker, environment-manager), `opus` on
the five auditor/architect agents (security-auditor, role-architect, team-validator,
spec-compliance-auditor, retrospective-analyst), `inherit` on the remaining 29. This is
what makes `aicost-model-routing` executable rather than advisory.

**`max-subagent-spawn-depth`.** New top-level teams.yaml setting, default 2, range 1–3,
emitted as `env.CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` in `.claude/settings.json`.

**Validation.** `spec-validator` now covers the failure modes that produce a file which
looks correct and registers as nothing: a non-conforming agent id, an unknown `tools-mode`
or `isolation`, a non-boolean `can-dispatch`, `allowlist` with no `preferred-tools`, and an
out-of-range or non-integer spawn depth.

## Two Corrections to the Implementation Spec

Both are recorded inline in `docs/planning/agents-teams/agent-dispatch-capability.md`.

1. **The settings template is `JSON.parse`d, not rendered.** The spec's
   `"CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "{{maxSubagentSpawnDepth}}"` would have
   survived verbatim into the generated file. The `env` block is built in
   `syncClaudeSettings` instead, alongside the permissions and hook wiring that are
   already merged the same way. Values are stringified — settings.json env values must be
   strings.
2. **The allowlist emission rule emitted two conflicting keys** — see above.

## Why Spawn Depth Is Not Derived From Handoff Depth

ADR-11 §4 argues this and the code now enforces it. `inferMaxHandoffChainDepth` returns 7
for this repo. A handoff chain runs one agent at a time and costs additively; a spawn tree
nests and multiplies, so depth 7 with any fan-out breaches `aicost-token-budget` on the
first `/orchestrate` run. Separate setting, default 2, which covers
orchestrator → team agent → specialist.

An out-of-range value **falls back to the default with a warning rather than clamping**.
Clamping 7 to 3 emits a plausible-looking number nobody asked for; the validator reports
the real error.

## Phase 4 — Protocol Reconciliation

Retort described two delegation protocols and never said which was in force. They are not
alternatives: the task file is the durable record, dispatch is the execution mechanism.
`orchestrate.md` and `team-TEMPLATE.md` now say so, selected by `dispatch.mode` in
settings.yaml (overlay key `dispatchMode`).

`orchestrate.md` gains the dispatch sequence, the spawn-depth cap, and a **team →
`subagent_type` routing table**. The table is not decoration — `assignees` names a team,
the Agent tool takes an agent id, and those coincide for `backend` but not for `testing`,
whose lead agent is `test-lead`.

Two of its instructions had become _wrong_, not merely incomplete, once Phases 1–3 landed:

- "pass `isolation: worktree` in the Agent tool call" — isolation is derived into the
  agent's own frontmatter now; the caller passing it is redundant at best.
- "Each team should accept or reject the task" — in native mode the dispatched agent does
  that, in its own context, holding its own lease.

`team-TEMPLATE.md` Step 0 branches on whether a taskId was supplied. A dispatched agent
reads its task directly instead of scanning, and does not fall through to backlog work the
orchestrator never delegated. It still takes the lease: being handed a taskId proves
assignment, not exclusivity.

## Two Defects Found Along the Way

**1. `resolveTeamAgents` left 8 of 13 teams with no agents.** It matched an agent
_category_ to a _team id_, but those are different vocabularies — the `backend` team's
agent is categorised `engineering`. Eight team commands had shipped with no Agent Personas
section, and the new routing table came out half empty, which is how it was noticed. Fixed
with an id-match fallback, plus explicit `agents:` lists for `security`, `docs`, and
`quality`, which name no agent and match no category.

**2. `coverage-report.yml` and `dependency-audit.yml` had never run.** Both guarded their
jobs with a job-level `if: hashFiles('package.json') != ''`. `hashFiles()` needs a
checked-out workspace and is only valid in a _step_-level `if`; at job level GitHub rejects
the entire file. No annotation, no log, 0s duration — and both are documented as
non-blocking, so nobody looked. **40/40 failures, on every branch, since they were added.**

A non-blocking check that never runs is indistinguishable from one that passed. The guards
are removed, not moved: the Rust/Python jobs are already gated at generation time, and the
Node jobs are `continue-on-error` with failure-tolerant steps.

`workflow-templates.test.mjs` now lints templates _and_ generated output for
workspace-only functions in job-level `if:`, asserts every generated workflow parses with
jobs and a trigger, and checks no `needs:` names a job that was not emitted. That last
assertion earned its place within minutes: the first version of the explanatory comment
contained a literal `{{#if hasLanguageRust}}`, which unbalanced the enclosing conditional
and leaked raw handlebars into the generated YAML.

## Open Questions

- **Name collisions — the one live decision.** 38 agents with generic names (`backend`,
  `data`, `infra`) occupy global agent-type space alongside plugin agents, and duplicates
  resolve by filesystem read order, which is not documented precedence. `agent-name-prefix`
  is specced but **deliberately not implemented here**: it changes every invocation name
  downstream and now interacts with the dispatch table, and the choice between a
  default-empty and a default-`retort-` prefix is a maintainer call rather than an
  implementation detail. The spec's own recommendation is default-empty with a `/doctor`
  collision warning — note that `/doctor` can only see retort's own agents, so it cannot
  detect a collision with an installed plugin agent.
- **Description-matching surface.** 38 dispatchable agents is a lot for automatic
  delegation to disambiguate. Phase 3 does narrow this indirectly — only 13 agents can now
  dispatch at all — but every one of the 38 is still a candidate for the main thread.
