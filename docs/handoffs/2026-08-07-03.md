## What Was Fixed

Three independent CI-config defects, all with the same failure mode — **invalid
config that produced no useful signal**, so each stayed broken unnoticed. Full
detail in `docs/history/bug-fixes/0005-2026-08-07-silently-broken-ci-config-defects-bugfix.md`.

1. **Required status check could never match.** Spec declared
   `'Branch Protection / branch-rules'`; GitHub reports the job id `branch-rules`.
   Every PR to `dev` was permanently `BLOCKED` — #573, #575 and #576 all merged via
   admin bypass. Also collapsed a duplicated contexts array in
   `setup-agentkit-branch-governance.{sh,ps1}` that carried the same wrong value
   independently, so fixing spec alone would not have been enough.
2. **`coverage-report.yml` and `dependency-audit.yml` had never run.**
   `hashFiles()` in a job-level `if:` is not an available function there, which
   invalidates the whole file — startup failure, zero jobs. The repo has had no
   coverage reporting and no dependency audit despite both appearing configured.
3. **Stop hook blocked on every dev-merge.** It skipped merge commits by message
   prefix, which misses `Merge origin/dev into <branch>`. Now detects them by
   parent count.

## Test Suite Is Flaky — Do Not Read One Run as a Regression

Four full runs of essentially the same code gave **1, 7, 13 and 5** failures.
Running the implicated files against **unmodified `dev`** reproduces them, so they
are pre-existing. `template-utils.test.mjs` — the only suite covering
`branchProtection` — passes all 240 tests.

Two contributors identified:

- `prettier.test.mjs` — Windows `core.autocrlf` artifact (CRLF checkout vs
  prettier's LF default). Zero-byte content diff; passes on Linux CI.
- `discover.test.mjs > detectCommitConvention() — git-log heuristic` — reads real
  `git log`, so it is sensitive to commits landing while it runs.

**Unexplained and worth its own investigation:** intermittent failures in
`sync-agent-features.test.mjs` and `check-coverage.test.mjs`.


They read `["Test","Validate","Branch Protection / branch-rules"]` earlier in this
same session, so someone applied the correction while this branch was in flight —
not this PR, which does not touch repo settings. PR #579 went from `BLOCKED` to
`CLEAN` as a result, and merged without admin bypass.

**This does not make the PR redundant — it makes it a regression guard.** Spec
still declared the broken value, so the next person to run
`setup-branch-protection.sh` or `setup-agentkit-branch-governance.sh` would have
silently re-broken `dev`. That is the gap this closes.

Still deliberately not automated: `.github/scripts/setup-branch-protection.sh`
also applies `requiredReviewCount: 1`, `requireCodeOwnerReviews: true`,
`requiredLinearHistory: true` and `requiredConversationResolution: true` — none
of which are set live. Running it wholesale is a much larger behavioural change
and should be a deliberate decision, so **do not run it casually just because the
contexts now match.**
