# ADR-15: Native Agent Dispatch — Emit Dispatchable Subagents, Keep Task Files as Record

**Status:** Accepted — all four phases implemented in
[#574](https://github.com/phoenixvc/retort/pull/574)
**Date:** 2026-08-07
**Deciders:** JustAGhosT
**Related:** [ADR-10 Tool-Neutral Agent Hub](./10-tool-neutral-agent-hub.md), [Implementation spec](../../planning/agents-teams/agent-dispatch-capability.md), [Bounded dispatch contract](../specs/SPEC-bounded-agent-dispatch-contract.md), [Worktree isolation rule](../../../.claude/rules/worktree-isolation.md)

## Context

Retort generates 38 agent personas into `.claude/agents/*.md` from `.agentkit/spec/agents/*.yaml`.
None of them are dispatchable.

Every generated file opens with an HTML comment rather than YAML frontmatter:

```text
<!-- GENERATED by Retort v3.1.0 — DO NOT EDIT -->
# Backend Engineer
## Role
```

Claude Code requires `name` and `description` frontmatter to register a subagent. Without it
the file is scanned, skipped, and never becomes an agent type. Confirmed empirically: in a
session rooted at this repository, the available-agent-types list contains every installed
plugin agent and none of retort's.

Three consequences follow:

1. **The task delegation protocol is role-play.** `orchestrate.md` specifies a task JSON
   lifecycle with `dependsOn`/`blockedBy` derivation, DFS cycle detection with SHA-256 cycle
   IDs, lock leasing with TTL, two-phase commit, and `HANDOFF_DEPTH_EXCEEDED` events. All of
   it executes inside a single main-thread context writing JSON files to itself. No second
   agent ever runs, so none of the concurrency machinery is exercised.

2. **The agent spec is far ahead of the emitter.** `accepts`, `depends-on`, `notifies`,
   `handoff-chain`, `decision-model`, `retry-policy`, `negotiation`, `lookahead`, and
   `confidence` are all modelled in YAML and all rendered as prose. They describe a runtime
   that does not exist.

3. **The worktree isolation rule cannot be followed.** It instructs callers to pass
   `isolation: "worktree"` to the Agent tool, and its own worked example dispatches
   `feature-dev:code-architect` — a plugin agent — because no retort agent is dispatchable.

Meanwhile the runtime capability the spec was reaching for already exists. Claude Code
subagents spawn subagents by default, up to three layers below the main conversation,
governed by `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`. At the depth limit the `Agent` tool is
withheld. A subagent that omits `tools:` inherits every tool available to subagents,
including `Agent`; one that lists `tools:` without `Agent` cannot delegate at all.

So the gap is not capability. It is emission.

## Decision

Emit real Claude Code subagents, and use native dispatch as the execution mechanism while
keeping task JSON files as the durable record.

### 1. Emit frontmatter

The agent template gains a YAML frontmatter block. `name` and `description` are required;
`model`, `color`, `disallowedTools`, `isolation`, and `tools` are derived. This single change
converts 38 documents into 38 dispatchable agents and is independently shippable.

### 2. `tools:` is omitted by default; restriction goes through `disallowedTools:`

The existing `preferred-tools` field (`Read, Write, Edit, Glob, Grep, Bash`) is **not**
promoted to `tools:`. It was authored as documentation — the template renders it under a
"Preferred Tools" heading — and as an allowlist it would silently strip `Agent`, `TodoWrite`,
`WebSearch`, `Skill`, and every MCP tool from all 38 agents, disabling nesting repo-wide as a
side effect of reinterpreting data that was never written for that purpose.

Agents therefore inherit the full subagent toolset, and capability is removed subtractively
via `disallowedTools`. Repos wanting strict allowlisting opt in per agent with
`dispatch.tools-mode: allowlist`.

### 3. Dispatch capability is opt-in per agent

A new `dispatch:` block in the agent spec carries `can-dispatch`, `tools-mode`, `model`, and
`when-to-use`. `can-dispatch` defaults by category — coordinator and lead roles get `Agent`,
leaf specialists do not. This keeps fan-out at the points where the team graph already models
it (`notifies`, `handoff-chain`) instead of letting any of 38 agents spawn any other.

### 4. Spawn depth is capped at 2 and is **not** derived from `maxHandoffChainDepth`

The two numbers measure different things and must not be conflated:

|             | `maxHandoffChainDepth` (currently 7)       | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` |
| ----------- | ------------------------------------------ | -------------------------------------- |
| Measures    | sequential handoffs across teams over time | nested live agent contexts             |
| Shape       | a chain — one agent active at a time       | a tree — every layer multiplies        |
| Cost        | additive                                   | multiplicative                         |
| Recorded in | task files, survives sessions              | process state, dies with the session   |

`backend → testing → docs → quality` is a legitimate depth-4 handoff chain and costs four
sequential agents. A depth-4 _spawn_ tree with fan-out 3 is up to 40 concurrent contexts.
Deriving the env var from `maxHandoffChainDepth` would emit `7` for this repo and violate the
project's own `aicost-token-budget` rule on the first `/orchestrate` run.

A separate `max-subagent-spawn-depth` setting is introduced, defaulting to `2`:
orchestrator → team agent → specialist. That covers every fan-out pattern retort actually
has. Depth 3 is available for repos that opt in.

### 5. Guardrails derive from `accepts`

`accepts` already classifies each agent's task types. It becomes the source for two runtime
fields:

- Agents whose `accepts` contains no write-capable type (`implement`, `fix`, `refactor`,
  `migration`, `test`, `document`) receive `disallowedTools: Write, Edit, NotebookEdit`.
- Agents whose `accepts` contains a code-writing type (`implement`, `fix`, `refactor`,
  `migration`, `test`) receive `isolation: worktree`.

This turns the worktree isolation rule from an instruction the caller must remember into a
property of the agent definition, and makes read-only agents structurally read-only.

### 6. Task files remain the record; native dispatch becomes the mechanism

Both protocols are kept, with clear roles:

- The orchestrator writes the task JSON first — it is the durable, portable, cross-session
  audit trail, and the only form that works on tools without native subagents.
- The orchestrator then dispatches the agent natively, passing the `taskId`.
- The subagent reads its task file, transitions it, and writes artifacts back on completion.
- The subagent's returned summary is what enters the orchestrator's context; the task file
  is what survives the session.

A `dispatchMode` setting selects the backend: `native` on Claude Code, `task-file` elsewhere.
The spec stays single-source, consistent with ADR-10's tool-neutral direction.

### 7. Native dispatch is an adapter, not the portable invocation contract

The generated `dispatch:` frontmatter controls a Claude agent type's static runtime capability:
whether it may spawn, which tools and model it receives, and whether it starts in a worktree. It is
not an `org.dispatch.v1` envelope and MUST NOT carry invocation-specific objective, context,
authority, lineage, or provider policy.

Each native invocation is governed separately by the bounded dispatch contract. In particular,
`max-subagent-spawn-depth` is a process safety cap, not `execution.currentDepth`;
`maxHandoffChainDepth` limits sequential task-file workflow, not authority nesting; and native reuse
does not decide whether an operation is a delegated child, same-agent continuation, or
equivalent-authority handoff. The portable envelope and authoritative run record make those
decisions before the adapter launches work.

This PR provides the native adapter surface but does not claim the R13 schema, fixtures, validators,
or resolved-policy persistence. Until those land, Retort treats this path as a legacy caller in the
contract's staged observe/warn rollout. Existing authorization, tool, worktree, and task-scope
controls remain mandatory and are never bypassed by rollout mode.

## Consequences

### Positive

- The delegation protocol executes instead of being narrated; lock leasing, cycle detection,
  and handoff depth limits become real code paths that can be tested.
- Context isolation actually materialises — the reason subagents exist. Per-dimension review
  fan-out in `/review` and `/project-review` stops consuming the main window.
- The worktree isolation rule becomes enforceable by construction.
- `model:` per agent makes the `aicost-model-routing` rule executable rather than advisory —
  Haiku for watchers, Opus for auditors.
- Spec fields that currently render as prose gain a runtime meaning, closing the gap between
  what `agents/*.yaml` models and what the emitter produces.

### Negative

- Token cost rises wherever fan-out is enabled; depth 2 with wide fan-out is the dominant
  new cost driver and needs budget guidance alongside it.
- 38 agents with generic names (`backend`, `data`, `infra`) enter global agent-type space and
  can collide with plugin agents. Duplicate `name` values resolve by filesystem read order,
  which is not a documented precedence. A `name-prefix` setting mitigates it; `/doctor`
  reports collisions.
- Description-matching quality becomes load-bearing. `role` is a capability statement, not a
  delegation trigger, so a `when-to-use` field is required or automatic delegation misfires.
- Every retort-managed repo regenerates all agent files on upgrade — a large one-time diff.
- Behaviour diverges between foreground and background subagents, since background subagents
  keep only a fixed subset of built-in tools regardless of frontmatter.

### Neutral

- `.agentkit/spec/` remains the single source of truth; no change to the authoring workflow.
- The change is additive and phaseable — Phase 1 (frontmatter only) ships without enabling
  any dispatch, and each later phase is independently revertible.
- Repos can opt out entirely via the feature flag; the generated output degrades to today's
  prose personas.

## Implementation Notes

Three things turned out differently from the decision as written. All are reflected in the
shipped code and in the [implementation spec](../../planning/agents-teams/agent-dispatch-capability.md).

1. **§2 understates the direction of the change.** Withholding `Agent` from leaf categories
   reads as "enables fan-out and its token cost". It does the opposite: before Phase 3 all
   38 agents inherited `Agent`, and after it only 13 coordinators hold it. The phasing table's
   "medium risk" describes what inverted defaults would cost, not what shipped.

2. **In `tools-mode: allowlist`, `tools:` is the only key emitted.** §2's emission rule would
   have produced `tools:` alongside `disallowedTools:` for a read-only agent — the same
   restriction expressed twice with no documented precedence between the two. The read-only
   denials are subtracted from the list instead. An allowlist that resolves to nothing falls
   back to `inherit` with a warning, because an empty `tools:` launches a subagent with no
   tools and fails at its first tool call rather than at sync time.

3. **§6's dispatch needs a team → agent routing table.** The task file names a _team_ in
   `assignees`; the `Agent` tool needs an _agent id_. They coincide for `backend` and not for
   `testing`, whose lead agent is `test-lead`. `orchestrate.md` now renders the mapping
   explicitly rather than leaving the orchestrator to guess.
