# Generated PowerShell scripts fail to parse under Windows PowerShell 5.1 Resolution - Historical Summary

**Completed**: 2026-08-07
**Bug ID**: Surfaced by a PSScriptAnalyzer `PSUseBOMForUnicodeEncodedFile` warning on a CodeRabbit review of PR #576
**PR**: [#581](https://github.com/phoenixvc/retort/pull/581)
**Severity**: High

## Problem Description

Every generated `.ps1` file failed to parse under Windows PowerShell 5.1 — the default
shell on Windows — making the PowerShell half of the toolchain effectively unusable there.

```powershell
powershell -NoProfile -File ./scripts/create-doc.ps1 -Type implementation -Title "Test"
# Missing closing '}' in statement block or type definition.
# ParserError: TerminatorExpectedAtEndOfString
```

The same files parsed clean under PowerShell 7 (`pwsh` 7.6.3), which is why the defect
survived unnoticed: anyone testing with `pwsh` saw nothing wrong.

This was long-standing, not a regression from a recent PR — `git show origin/dev:scripts/create-doc.ps1`
and the older `6d2d4e6c` revision produce the same parse errors under 5.1.

## Root Cause Analysis

Two independent 5.1 incompatibilities, the second masked by the first.

**1. Encoding (the reported defect).** Generated `.ps1` files were written as UTF-8
_without_ a BOM. Windows PowerShell 5.1 decodes a BOM-less file as ANSI/Windows-1252
rather than UTF-8. Multi-byte UTF-8 sequences — em-dashes in comments, `ℹ️` in
`Write-Host` strings — were therefore mangled into replacement characters that could
swallow a string terminator, breaking the parse of the entire file. PowerShell 7+
defaults to UTF-8 and is unaffected.

Which files actually broke was luck-of-the-draw: it depended on where the mangled bytes
landed relative to a string terminator. `scripts/update-changelog.ps1` contained four
non-ASCII characters and parsed fine; `scripts/create-doc.ps1` contained four and did
not. That non-determinism is the argument for a blanket rule rather than per-file
character stripping.

**2. `Join-Path` arity (uncovered once files parsed).** `Join-Path` accepted at most two
path segments until PowerShell 6 added `-AdditionalChildPath`. `create-doc.ps1` passed
three at line 35 and seven at line 111, producing
`A positional parameter cannot be found that accepts argument 'history'` at runtime.
This was invisible while the file could not be parsed at all.

## Solution Implemented

Fixed at the sync engine's file writer rather than by stripping non-ASCII from each
template — one change covering every current and future `.ps1` template.

The BOM is applied unconditionally for `.ps1`, not only when the content happens to
contain non-ASCII, so a template that gains an em-dash later cannot silently become
unparseable, and the rule stays deterministic as content changes.

Verified safe before adopting the blanket rule: nothing execs a `.ps1` via its shebang
(hooks are invoked as `pwsh -NoLogo -NoProfile -File ...`, and only `.sh` output receives
`chmod +x`), so a leading BOM cannot break shebang detection.

### Code Changes

- **`.agentkit/engines/node/src/fs-utils.mjs`**: added `UTF8_BOM`, `needsUtf8Bom()`, and
  the idempotent `applyUtf8Bom()`; applied in `writeOutput`.
- **`.agentkit/engines/node/src/platform-syncer.mjs`**: local `writeOutput` now applies
  the BOM — covers `syncDirectCopy` and Claude hook output.
- **`.agentkit/engines/node/src/scaffold-engine.mjs`**: re-applies the BOM when writing a
  three-way-merge result, so a merge whose winning hunk came from the user's BOM-less
  side cannot drop it.
- **`.agentkit/templates/scripts/create-doc.ps1`**: nested the two multi-segment
  `Join-Path` calls into 5.1-compatible two-argument form.
- **Four hand-written scripts** outside the sync pipeline (no template, absent from
  `.agentkit/.manifest.json`) received BOMs directly, since nothing re-applies one for
  them: `.claude/hooks/init-state.ps1`, `scripts/reset-state.ps1`,
  `scripts/validate-state.ps1`, and `scripts/retort-sync.ps1` (the last parsed correctly
  but carried `⚠️` and em-dashes — the same latent defect).

### Testing

- **Unit Tests**: `fs-utils.test.mjs` — `needsUtf8Bom` extension matching (including
  case-insensitivity and the `.sh` exclusion), `applyUtf8Bom` idempotency and
  non-string pass-through, and `writeOutput` byte-level assertions covering the exact
  characters that broke 5.1.
- **Integration Tests**: `powershell-encoding.test.mjs` — a repo-wide guard asserting
  (a) any tracked `.ps1` containing non-ASCII bytes carries a BOM, and (b) every `.ps1`
  under the sync-owned directories carries one unconditionally. The guard was
  mutation-checked by stripping a BOM and confirming it fails with an actionable message.
- **Manual Testing**: AST parse check of all 43 tracked `.ps1` under both `powershell`
  5.1 and `pwsh` 7.6.3; full end-to-end execution of `create-doc.ps1` under 5.1 (this
  document was generated by that run).

## Verification

Parse-checked every tracked `.ps1` under both shells via
`[System.Management.Automation.Language.Parser]::ParseFile`, then ran `create-doc.ps1`
end-to-end under 5.1. Sync was run twice to confirm idempotency — no drift, no BOM churn.

### Before/After Comparison

|        | Windows PowerShell 5.1     | PowerShell 7.6.3 |
| ------ | -------------------------- | ---------------- |
| Before | 12 files failing to parse  | clean            |
| After  | 0 executable files failing | clean            |

`create-doc.ps1` progressed from `ParserError: TerminatorExpectedAtEndOfString` (before),
to a `Join-Path` parameter-binding failure (after the encoding fix alone), to successful
execution (after both fixes).

### Regression Testing

`powershell-encoding.test.mjs` fails the build if a non-ASCII `.ps1` ever ships without a
BOM, or if the sync writer stops emitting one.

## Impact Assessment

Any contributor on Windows using the default shell. Every documented `./scripts/*.ps1`
entry point was unusable; the `.sh` equivalents were the only working path, which is
invisible from the documentation.

## Prevention Measures

- Encoding is now a property of the writer, not of individual templates, so new `.ps1`
  templates are correct by default.
- The regression guard asserts the invariant across the whole repo rather than a fixed
  file list, so newly added scripts are covered automatically.
- Parse-check `.ps1` changes with `powershell` (5.1), not only `pwsh` — 7.x silently
  tolerates both defects fixed here.

## Lessons Learned

A fix that makes a file _parse_ is not the same as making it _work_. The encoding fix
immediately exposed a second 5.1 incompatibility (`Join-Path` arity) that had been dead
code behind the parse failure — verifying by execution rather than by parser check alone
is what caught it.

Testing on the newer runtime hid the bug rather than revealing it. `pwsh` 7 tolerates
both BOM-less UTF-8 and multi-segment `Join-Path`; 5.1 tolerates neither.

## Known Remaining Issues

- **`.agentkit/bin/setup-branch-protection.ps1:84`** fails to parse under _both_ 5.1 and
  pwsh 7: `Variable reference is not valid. ':' was not followed by a valid variable name
character`. This is a genuine pre-existing syntax bug, unrelated to encoding, and was
  left for a separate fix.
- `.agentkit/templates/**/*.ps1` intentionally remain BOM-less. Templates are the input
  to rendering, never executed as PowerShell, and a leading BOM would precede the
  `<# agentkit: scaffold: ... #>` frontmatter and break scaffold-mode detection. Their
  BOM is applied at render time.
- The nine `.agentkit/bin/*.ps1` CLI scripts are pure ASCII and therefore decode
  identically under ANSI and UTF-8; they are covered by the non-ASCII arm of the
  regression guard should that ever change.
